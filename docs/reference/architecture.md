# How the code is organised

A map for anyone changing the site. The rules for each part (design, motion, money, security) are in [`CLAUDE.md`](../../CLAUDE.md), and the reasons behind them in [`decisions.md`](decisions.md).

## The big picture

```
Browser ── the shop (app/(site))  ─┐
        └─ the admin (app/(admin)) ─┤── server actions and /api routes ── src/server/* ── PostgreSQL (Neon)
                                    │                                       └── providers: SSLCommerz, aamarPay,
Couriers and gateways ── webhooks ──┘                                           Pathao, Steadfast, RedX, CarryBee,
                                                                                4 SMS gateways, 4 email services,
                                                                                Vercel Blob (keys: integrations)
Vercel Cron ── /api/cron/* (every 10 and 30 minutes)
```

- **Next.js 16, App Router**, with two separate root layouts: the shop and the admin never share CSS or scripts. The admin never loads GSAP, Lenis or three.js.
- **Pages are server components.** They read the database directly through `src/server/*` and `src/db/*`. Client components are only for interaction and animation.
- **Writes** go through **server actions** (admin) and **route handlers** (`/api/*`: checkout, payments, couriers, cron, downloads). Each checks the caller's permission and validates its input with Zod.
- **Money and stock** change only inside database transactions (`withTx`). Every stock change is a row in the stock ledger.

## How an order moves through the code

1. **Checkout** (`app/(site)/checkout`) calls `/api/checkout/otp`, then `/api/checkout/quote`, then `/api/checkout/place`. Prices, fees and coupons are recalculated on the server (`server/checkout/pricing.ts`, `quote.ts`), and the order is written with its stock held or sold (`server/orders/place.ts`).
2. **Payment** (`server/payments`): `/api/payments/start` opens the gateway. Its IPN and the customer's return both go through `settleNotice()`, which pays the order only after validating with the provider.
3. **Fulfilment:** every status change goes through `transitionOrder()` (`server/orders/manage.ts`), which follows `state.ts`, writes the timeline, and handles stock and payment side effects.
4. **Shipping** (`server/shipping`): `sendToCourier()` creates the parcel. Courier statuses (webhook, cron poll, or the test courier) go through `applyCourierStatus()`, which moves the order along the state machine.
5. **The receipt and invoice** both render one `InvoiceData` (`server/invoice`), as an email (React Email) and a PDF (React PDF).
6. **Reports** read the same orders through one sales rule (`server/reports/metrics.ts`).

## Providers, and working without keys

Every paid service sits behind an interface with a local stand-in, so the whole flow runs with no accounts:

| Service | Interface | Stand-in | Real |
|---|---|---|---|
| Payments | `server/payments/types.ts` | test gateway (`mock.ts`) | SSLCommerz, aamarPay (tried in the owner's order, falling back to the next) |
| Couriers | `server/shipping/types.ts` | test courier (`mock.ts`) | Pathao, Steadfast, RedX, CarryBee |
| SMS | `server/providers/sms` | prints to the terminal and `.data/sms.log` | BulkSMSBD, SSL Wireless, Alpha SMS, MiMSMS (tried in the owner's order, falling back to the next) |
| Email | `server/providers/email` | saves to `.data/outbox/` | Resend, Brevo, Postmark, your mailbox over SMTP (same order and fallback) |
| Photos | `server/providers/storage` | `.data/uploads/` | Vercel Blob |

Every real provider is set up in **Admin → Integrations** (`server/integrations`): its keys are sealed in the `integrations` table, it can be tested and switched on or off, and the old environment variables still work as a fallback. Without any provider, two fallbacks need no keys at all: bKash or Nagad paid by hand (`server/payments/manual.ts`) and "other courier" (`server/shipping/manual.ts`).

The test gateway and test courier refuse to run on the live site (`server/test-mode.ts`).

## Tests

- `npm test`: unit tests (`tests/unit`), no database.
- `npm run test:db`: integration tests (`tests/db`) against your local PostgreSQL. They create and remove their own test data.
- `npm run check`: lint, typecheck, unit tests and a production build together.
